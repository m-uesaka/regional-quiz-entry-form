These guidelines foster clean, readable, and maintainable documentation.

This file holds the rules common to every language. After loading it, read
only the reference files that match the task:

| When you write | Read |
| --- | --- |
| Python docstrings | [`reference/python.md`](reference/python.md) |
| TypeScript, JavaScript, or Svelte doc comments | [`reference/typescript.md`](reference/typescript.md) |
| Anything in Japanese | [`reference/japanese.md`](reference/japanese.md) |
| A Markdown document that a skill outputs | [`writing_rules.md`](writing_rules.md) |

For a programming language with no reference file, use the doc comment
format that is standard for that language and apply the common rules below.

# Which natural language to write in

Decide the language in this order, and stop at the first one that applies.

1. The language the user asks for.
2. The language of the file or document being edited.
3. The language of the existing documentation in the project.
4. English.

- Do not mix languages within one file or one document.
- Never translate identifiers, section names, tags, or exception messages.
  They stay as written in the code.

# Documentation

"Doc comment" below means a Python docstring, a JSDoc/TSDoc comment, or the
equivalent in another language.

- Always add doc comments.
  - Start with a one-line summary in the imperative mood. Avoid the
    descriptive mood ("This function does...").
  - Stick to the line length limit of the project's formatter, except if the
    line contains a long URL.
  - Doc comments must describe arguments, exceptions, and return values as
    appropriate.
  - The only acceptable case for not having doc comments is tests.
- Do not write in a doc comment what the signature already states: neither
  the types nor the default values of arguments.
- When a function raises an exception, document it. The description should be
  the same as the exception message.
- Keep the consistency of implementation and doc comments.
  - Check and update the doc comments if the specification or implementation
    are changed.
  - Do not contain the thinking process in the comments.

## Parent and child class

- Do not repeat in the child the documentation of inherited members. Document
  only what the child adds or changes, and point to the parent.
- See the reference file of each language for an example.

## Documents generated by skills

- The Markdown documents that a skill writes as its output (a task list, a
  review report, a ticket, etc.) follow
  [`writing_rules.md`](writing_rules.md).
- These rules do not apply to doc comments, code comments, or the
  documentation in `docs/`.

## Additional documentation

- We add additional documentation in `docs/` at the root of the repository.

### Figures

- When an algorithm or a data flow is hard to follow in text, add a figure to
  visualize it.
- Write the labels in the same language as the document that shows the
  figure.
- The figure should be added as follows.
  - The file format is `.drawio.svg`.
  - Please create the file in a format that is editable in drawio as
    "mxGraphModel only" (without an SVG wrapper, using drawio's standard
    `.drawio.svg` format).
    - When you create the figure, please follow two steps as follows.
      - First, create a `drawio.svg` file in a non-editable format.
      - Then, refer to other figures in the repository (check existing
        `.drawio.svg` examples that include `mxGraphModel`) and save it in the
        same format (editable) as the `mxGraphModel` format.
  - Please check if the figure can be opened in a format editable by drawio.
  - The background of the figure should be white (not transparent).
  - Do not need the class diagram, and other UML figure.
